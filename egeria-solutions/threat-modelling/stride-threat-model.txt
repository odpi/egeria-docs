## How to use this template

This template follows the steps of the [Threat Modelling](https://egeria-project.org/egeria-solutions/threat-modelling/overview/) solution.  Work through it from top to bottom:

1. **Model the system** - describe the components being reviewed, the actors (legitimate and malicious) that interact with them, and the data flows between them.  If the components are already in Egeria (for example from an information supply chain), skip the *Create Solution Component* commands and use their qualified names in the links.
2. **Record the risks** - for each component, work through the six STRIDE categories using the questions below.  Each concrete way that a threat could affect the component is a risk, rated for likelihood and impact, linked to its STRIDE threat and scoped to the component.
3. **Record the mitigations** - each control that reduces a risk, linked to the risk it addresses.

The six STRIDE threats are already defined in Egeria's Core Content Pack, which every Egeria server loads, so this template refers to them rather than creating them:

| STRIDE category | Qualified name |
|---|---|
| Spoofing | `Threat::STRIDE::Spoofing` |
| Tampering | `Threat::STRIDE::Tampering` |
| Repudiation | `Threat::STRIDE::Repudiation` |
| Information disclosure | `Threat::STRIDE::InformationDisclosure` |
| Denial of service | `Threat::STRIDE::DenialOfService` |
| Elevation of privilege | `Threat::STRIDE::ElevationOfPrivilege` |

The mitigations can be your organization's own controls, or controls from a standard catalog such as NIST SP 800-53, which is available in Egeria's Security Content Pack (for example `NIST SP 800-53 Rev 5::AC-2`).

Replace every value in square brackets.  Copy a command block (from `___` to `---`) as many times as you need - for example, once per component, per actor, per data flow, per risk and per control.  Text outside the command blocks, like this section, is ignored by Dr.Egeria, so it can be used for notes from the review.

Set `[Org]` to your organization's prefix for qualified names (for example `CocoPharma`), and `[Model]` to a short name for this model with no spaces.

Validate the file before processing it:

```
dr_egeria --validate stride-threat-model.md
dr_egeria --process stride-threat-model.md
```

### STRIDE questions

| Category | Ask of each component and data flow | Typical mitigations |
|---|---|---|
| **S**poofing | Could an actor pretend to be another user, component or system?  How are callers authenticated? | Authentication, protecting and rotating secrets, removing obsolete identities |
| **T**ampering | Could data or software be changed without authorization - at rest, in transit or in the build pipeline? | Authorization, hashes and signatures, secure storage, tamper-resistant protocols |
| **R**epudiation | Could someone deny an action because there is no reliable record of who did it? | Audit trails, timestamps, digital signatures |
| **I**nformation disclosure | Could data be read by someone who should not see it - including configuration, credentials and logs? | Authorization, encryption, data minimization, protecting secrets |
| **D**enial of service | Could the component be made unavailable, or starve others of resources? | Throttling, quotas, redundancy, quality of service |
| **E**levation of privilege | Could an actor gain more access than they were granted? | Least privilege, privilege separation, role-based access control |

Consider all the kinds of data a component handles: configuration data, authentication data, persistent data, data in transit, session or state data, and temporary data.

## Part 2: The risks

Repeat this group of three commands for each risk found.  Name the risk after what could happen, not after the category - for example "Stolen administrator password used to change patient records".

Record the likelihood and impact in the description, and the overall rating in *Importance* (for example Low, Medium, High or Critical).  The implications are what would need to be true for the organization to say it has responded.
