### Details of this release

??? functional "Recording decisions, their assessments and outcomes"
    Egeria can now record the decisions that an organization makes, what was assessed to make them, and what resulted from them.

    * A [*Decision*](/types/0/0018-Decisions) describes the decision: its summary, scope, usage, importance, disposition (status) and implications, notes on why it was made, and when it starts, was last reviewed, is next due for review and expires.  It is an authored element, so it has authors and a content status like a governance definition.
    * The *Assessment* relationship links an element that was assessed to the decision that the assessment contributed to.  It records who made the assessment, when, when it expires and any notes.  It is a [multi-link](/concepts/uni-multi-link) relationship, so the same element can be assessed many times for the same decision.
    * The *Outcome* relationship links a decision to an element that represents an outcome of the decision, with the importance and disposition of that outcome.

    Decisions are maintained through the [Governance Officer API](/services/omvs/governance-officer/overview), and so are available through each of the governance view services that share it.  There are requests to create (directly or from a template), update, delete, retrieve and search for decisions, and to attach and detach outcomes.  Attaching an assessment returns the unique identifier of the new relationship, which is then used to update or detach it.  Connectors can work with decisions through the new *DecisionClient* in their context.

??? functional "Describing data values"
    Egeria can now describe particular data values, such as the values used to configure a process instance (for example, an analytic model run).  They help to explain why different runs of the same process produce different results.

    * A [*DataValue*](/types/2/0208-Data-Values) describes a value's format, length, data type and usage, and can carry a fingerprint or hash of its content.  The value may be primitive, or a complex value such as an array, map, nested structure or graph.
    * A *LiteralDataValue* is a data value that holds the data in open metadata, as a string, a list of strings or a map.
    * The *DataValueSource* relationship links a data value to the asset for the digital resource where the data is stored, for values that are too large or too sensitive to copy into open metadata.
    * The *ProcessingVariable* relationship links an element, such as a process, to a data value used to configure its processing, with the position in which it is passed.
    * The *EmbeddedDataValue* relationship places one data value inside another, with its position.
    * The [*SupportedVariableType*](/types/5/0520-Process-Schemas) relationship links an element, such as a process, to the schema types that describe the kinds of data value it can be configured with, with their position and cardinality.

    Data values are maintained through the [Data Engineer API](/services/omvs/data-engineer/overview), which has requests to create (directly or from a template), update, delete, retrieve and search for data values, and to attach and detach each of the three data value relationships.  Supported variable types are attached and detached through the [Schema Maker API](/services/omvs/schema-maker/overview).  Connectors can work with data values through the new *DataValueClient* in their context.

??? functional "Project targets and source code branches"
    * The new *ProjectTarget* relationship identifies an element that a [project](/types/1/0130-Projects) is working on.  It is attached and detached through the [Project Manager API](/services/omvs/project-manager/overview), and each element shows the projects that are working on it.
    * The new *Branch* classification identifies an element that holds the files for a specific branch of a source code repository, with the branch's name, purpose, scope and URL.  It is set and removed through the [Devops Pipeline API](/services/omvs/devops-pipeline/overview).

??? functional "Support for Apache Parquet files"
    Egeria can now read, catalogue and survey [Apache Parquet](https://parquet.apache.org/) files in the same way that it does CSV files.  See [Working with Apache Parquet files](/egeria-solutions/leveraging-files/overview/#working-with-apache-parquet-files).

    * The new *Parquet File Store* connector reads the description of a Parquet file from the file's footer: its columns and their data types, the number of rows, its row groups, the compression used, and the tool that wrote it.  This works whatever the format version, data page version, encoding and compression of the file, and adds no new dependencies to Egeria.
    * The rows in the file are read through the DuckDB JDBC driver, which is already shipped with the OMAG Server Platform.  In a runtime without the driver, the connector still describes the file, but a request to read a row fails.
    * The *Parquet Data File* template in the [Core Content Pack](/content-packs/core-content-pack/overview) now creates a connection that uses the new connector.
    * The new *Parquet Tabular Data Set* and *Parquet Tabular Data Set Collection* connectors present a Parquet file, or a directory of Parquet files, as a [tabular data set](/concepts/tabular-data-set).  Each has a deployed implementation type and a template in the Core Content Pack.  They use the same `directoryPathName`, `tableName` and `tableDescription` configuration properties as their CSV equivalents.
    * The new `survey-parquet-file` survey records measurements for the file and a profile for each column, including the counts of each value for columns that have up to 100 distinct values.  It is the survey listed for the *Parquet Data File* technology type.
    * The [Liskov Data Sharing Hub Manager](/patterns/harvest-and-publish/overview/#the-liskov-data-sharing-hub-manager) includes Parquet files in the data dictionary of a data sharing hub, whether the file is a member of the hub or has been catalogued from a directory that is a member.

    The Parquet connectors are read-only.  A nested column (an array, map or structure) is catalogued as a single column with a data type that describes its structure.

??? functional "File system normalization in data sharing hubs"
    The same directory or file can be catalogued under different path names, because each system or container sees it through its own mount point.  The new [File System Normalization](/features/file-system-normalization/overview) feature page describes how the `localMountPoint` and `canonicalMountPoint` properties resolve this, and how linking a [*FileSystem*](/types/0/0056-Resource-Managers/#filesystem) to a *FileFolder* tells Egeria which mount points apply to it.

    The [Liskov Data Sharing Hub Manager](/patterns/harvest-and-publish/overview/#the-liskov-data-sharing-hub-manager) now normalizes the path names of the directories that are members of a data sharing hub.

    * Liskov converts a directory's `pathName` to its canonical path name before it looks for the files catalogued from it.  Previously, the files in a directory that was catalogued with a local path name were never found.
    * The directory, and every folder and file catalogued beneath it with a local path name, has its `pathName` set to the canonical path name.  Their qualified names and connections are not changed.
    * Folders, or files, that then have the same canonical path name are linked as potential duplicates, using a *PeerDuplicateLink* relationship with a status of `DISCOVERED`.
    * The mount points are taken from the nearest *FileSystem* linked to the directory, or to one of its parent folders, by a *CapabilityAssetUse* relationship.  If there is none, they come from the [catalog target](/concepts/catalog-target) that the directory is catalogued through, then from Liskov's own new `localMountPoint` and `canonicalMountPoint` configuration properties, and then from the defaults used by the folder cataloguers.

    The [Mendel Automated Duplicate Manager](/features/duplicate-management/overview/#the-mendel-automated-duplicate-manager) has a second ground for confirming a duplicate without referring it to a steward: both elements are files, or both are folders, and they have the same `pathName`.  It withdraws the confirmation if the path names later differ.

??? functional "Solution boundaries in solution blueprints"
    The components and roles in a [solution blueprint](/concepts/solution-blueprint) can now be organized into a hierarchy of solution boundaries, to make a large blueprint easier to understand.

    * A [*SolutionBoundary*](/types/7/0740-Solution-Blueprints) is a collection of solution components, solution roles and other solution boundaries.  It is linked to its solution blueprint (or to another solution boundary), and to its members, using the *CollectionMembership* relationship.
    * It is a type of [*DesignModelBoundary*](/types/5/0565-Design-Models), which is the new general-purpose collection for organizing the content of any design model.
    * When a solution blueprint is retrieved, each solution boundary in it is returned with its members nested inside it, and is shown in the blueprint's mermaid graph as a box, with a white border and title, around its members.  Solution linking wires are shown between the components whichever boundary they are in.
    * A solution boundary is retrieved with the same content as a solution blueprint, and has the same mermaid graph showing the components and roles inside it.

    Solution boundaries are maintained through the [Solution Architect API](/services/omvs/solution-architect/overview), which has requests to create (directly or from a template), update, delete, retrieve and search for solution boundaries.  Members are added to a solution boundary through the [Collection Manager API](/services/omvs/collection-manager/overview), in the same way as they are added to a solution blueprint.

??? functional "Run-level lineage and configurable templates in the Open Lineage Cataloguer"
    The [Open Lineage Cataloguer](/egeria-solutions/leveraging-open-lineage/overview/#cataloguing-the-events) has two new capabilities.

    * The new *catalogRunLineage* configuration property catalogues each run as a *TransientEmbeddedProcess* owned by the job's process, and links the run to the datasets that it read and wrote.  The lineage is still maintained on the job's process, so the job shows every dataset that any of its runs has used and each run shows the datasets that it used.  The existing *catalogRuns* property is unchanged: it catalogues the run without its own lineage.  Both are off by default.
    * The catalog templates used for jobs and datasets that are not catalogued yet are now selected through *template names* built from the values in the events, such as `job:AIRFLOW:DAG` and `dataset:snowflake`.  The mapping of template names to templates in the content packs is the default.  The *templates* property of a [catalog target](/concepts/catalog-target) attached to the cataloguer can replace the template for a name, or supply a template for an integration or namespace scheme that has no default.  See [Template names](/egeria-solutions/leveraging-open-lineage/overview/#template-names) for the list of names and their default templates.

??? functional "Changes to the open metadata types"
    * New model [0018 Decisions](/types/0/0018-Decisions) adds the *Decision* entity and the *Outcome* and *Assessment* relationships.
    * New model [0208 Data Values](/types/2/0208-Data-Values) adds the *DataValue* and *LiteralDataValue* entities and the *DataValueSource*, *ProcessingVariable* and *EmbeddedDataValue* relationships.
    * New model [0520 Process Schemas](/types/5/0520-Process-Schemas) adds the *SupportedVariableType* relationship.
    * [0130 Projects](/types/1/0130-Projects) has a new *ProjectTarget* relationship.
    * [0280 Software Development Assets](/types/2/0280-Software-Development-Assets) has a new *Branch* classification.
    * [0565 Design Models](/types/5/0565-Design-Models) has a new *DesignModelBoundary* entity, which is a type of *Collection*.
    * [0740 Solution Blueprints](/types/7/0740-Solution-Blueprints) has a new *SolutionBoundary* entity, which is a type of *DesignModelBoundary*.
    * Each of the new relationships has a label and a description.  The elements linked by them are returned with every element that is retrieved through the view services, and are shown in its mermaid graph.

??? functional "Bug fixes"
    * An [integration connector](/concepts/integration-connector) that is driven by the integration daemon's refresh thread is now disconnected when it is restarted, for example after its configuration properties are updated, and when the daemon shuts down.  Previously the instance being replaced was left running, and if it had registered for Open Lineage events, Bitol documents or DCAT documents it carried on receiving them alongside the new instance.

### Upgrade notes

* The `CSVFileConfigurationProperty` enumeration in the Open Metadata Framework (OMF) has been renamed to `TabularFileConfigurationProperty`, since it is now shared by the CSV and Parquet tabular data set connectors.  The names of the configuration properties it defines are unchanged, so only Java code that refers to the enumeration needs to change.
* The Liskov Data Sharing Hub Manager changes the `pathName` of the directories that are members of a data sharing hub, and of the folders and files catalogued beneath them, to their canonical path names.  Searches that rely on the local path names of these elements need to use the canonical path names instead.  See [File System Normalization](/features/file-system-normalization/overview).
